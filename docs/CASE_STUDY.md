# 案例：连锁门店运营跟进自动化（"数字员工"批量执行系统）

> **一句话概述**：一套把「拉取经营数据 → 生成门店数据卡片 → 企业微信定向发送 → 截图回传飞书归档」全流程无人化的自动化系统。单批 30 家门店由人工 2-3 小时压缩到约 30 分钟无人值守（系统吞吐 1 分钟/店），异常单店自动隔离，随时可暂停/恢复，全程数据可追溯。
>
> **文档性质**：脱敏案例文档。文中品牌、门店、人员、内部系统标识均为泛化处理，不涉及任何真实商业数据。

---

## 一、项目背景

**客户类型**：全国性连锁门店品牌（跨多省市，本地生活/餐饮零售行业）。

**原有作业流程（纯人工）**：

1. 运营人员登录飞书多维表格，逐店查看当天的经营指标（流量、转化、交易、评价等 20 项）
2. 手工整理每店数据 → 截图或制图
3. 打开企业微信，在通讯录中逐层搜索「门店部门」→ 找到对应店长 → 私聊发送数据与运营建议
4. 发送完成后截取会话记录 → 回到飞书逐条上传截图 → 手工记录跟进时间

**痛点**：

| 痛点 | 具体表现 |
|---|---|
| 重复劳动量大 | 单店全流程 10+ 个操作步骤，数百家门店每天/每轮反复执行 |
| 易错 | 店长与门店对应关系复杂（联营/直营/协店组），人工容易发错对象 |
| 无法留痕追溯 | 是否发送、是否发送成功、发送给了谁，依赖人工记忆 |
| 数据链路断裂 | 发送结果与飞书业务表之间靠人工搬运，无法形成闭环 |
| 停不下来 | 一旦开始只能做完，中途被打断就要从头核对 |

---

## 二、方案概览

系统以「飞书多维表格」为唯一数据源和结果归档地，以「企业微信桌面端」为触达通道，全程代码化执行：

```
飞书多维表格（数据源，只读指定表）
        │  ① 拉取记录：门店 / 店长 / 20 项经营指标 / 跟进状态
        ▼
   目标筛选引擎
        │  ② 过滤：排除已完成、缺信息、人工核对名单、非跟进类型
        │  ③ 优先级排序：不达标直营店 → 不达标联营店 → 达标直营店 → 达标联营店
        ▼
   门店数据卡片生成（一店一图，HTML → 无头浏览器渲染 PNG）
        │  ④ 数值智能格式化：百分比 / 千分位 / 达标红绿标注
        ▼
   企业微信自动化（GUI 级操作 + OCR 多重校验）
        │  ⑤ 搜索门店部门 → 定位店长 → 打开会话 → 发送话术 + 数据卡片
        │  ⑥ 校验发送结果（输入框 OCR + 粘贴后像素差异检测）
        ▼
   会话截图回传飞书（写回指定表）
        │  ⑦ 上传截图至「跟进截图」字段 + 写入跟进时间
        │  ⑧ 上传成功后自动删除本地图片（证据只留飞书）
        ▼
   运行状态持久化（state.json + 分日日志）
        │  ⑨ 成功/失败逐店记录；中断后重跑自动跳过已完成（幂等）
```

## 三、核心技术能力（工程可信度部分）

### 3.1 企业微信 GUI 自动化（无 API 场景下的稳定操作）

企业微信桌面端没有开放的个人消息发送 API，系统采用「UI 自动化 + 视觉校验」方案，每一跳操作都有验证，不盲发：

1. **窗口接管**：枚举窗口句柄精确锁定「企业微信」主窗口，线程级前台激活（兼容 Windows 焦点限制），自动最大化并对齐坐标系
2. **搜索验证**：输入门店名后，OCR 识别搜索框文本，字符覆盖率 < 70% 直接报错，不进入下一步
3. **部门定位**：OCR 识别通讯录结果，字符覆盖率模糊匹配找到目标部门
4. **店长候选人打分排序**：对部门成员逐条 OCR，按「姓名精确匹配 / 前缀匹配 / 模糊匹配 + 职务是否为店长 + 是否为备用人员」加权排序，自动排除「联营店长、无、空」等噪声
5. **身份双校验**：点击候选人后，必须同时通过「个人名片姓名校验」+「所属门店校验」，才点击「发消息」
6. **会话标题校验**：进入会话后再次校验标题中的店长姓名，三关全过才允许发送
7. **兜底策略**：部门成员列表展开失败时，自动切换「按人名全局搜索」路径，并优先选择副标题包含目标门店的候选人

### 3.2 发送结果验证（不"盲发"）

- **文字发送**：粘贴后 OCR 识别输入框内容，用多个文本片段做探针比对，校验通过才按回车
- **图片发送**：粘贴前后对输入区做像素级差异检测（阈值 0.2%），确认图片真实进入编辑区才发送；失败自动重试 1 次后放弃并记录
- **防重复**：发送前落地「文字已发送」临时标记（2 小时有效），中断重跑不会给同一店长发两遍话术

### 3.3 幂等与断点续跑

- 每店结果（成功/失败/截图路径/时间戳）持久化到运行状态文件
- 重跑时自动跳过已完成门店，失败门店保留证据可单独重试
- 写回飞书前二次检查字段是否已被他人填写，有内容则跳过上传（防止覆盖人工操作）

### 3.4 人在回路：全局暂停热键

- `Ctrl+Z` 一键暂停 / 再按恢复（低级键盘钩子独占拦截，不干扰其他程序）
- 暂停在安全点生效：当前店未完成则不发送、不误发，恢复后自动重跑该店
- 适用场景：需要临时人工介入、处理突发消息、开会暂停等

### 3.5 安全与数据边界

| 边界 | 实现 |
|---|---|
| 表级白名单 | 代码硬编码仅允许操作指定的单一多维表格，其他表一律拒绝 |
| 密钥管理 | 应用凭证通过环境变量注入，不落盘、不入库、不进日志 |
| 发送节流 | 每店间隔 8-15 秒随机，模拟人工节奏，降低风控风险 |
| 数据清理 | 飞书上传成功后自动删除本地截图（卡片图/会话图/debug 图）；失败门店保留证据 |
| 运行隔离 | 任一门店异常只影响本店，批次不中断；企业微信掉线自动等待 90 秒恢复 |
| 人工核对清单 | 飞书店长与企微实际成员不一致的店自动跳过并登记原因，交由人工确认，绝不猜测发送 |

### 3.6 技术栈

Python · 飞书开放平台 API（多维表格 / 云文档素材）· uiautomation + Win32（Windows UI 自动化）· RapidOCR（本地离线 OCR）· Playwright（卡片渲染）· Pillow（图像处理）· 自研低级键盘钩子（暂停控制）

## 四、效果量化

> 口径说明：运行参数类为系统实测配置；效率对比为基于真实操作步骤与节流参数的保守测算，非营销数据。实际收益随门店信息规范程度浮动。

| 指标 | 人工模式 | 系统模式 |
|---|---|---|
| 单店操作步骤 | 10+ 步（查数据、制图、搜索、核对、发送、截图、上传、记录） | 0 步（全自动） |
| 单店耗时 | 约 3-5 分钟（含切换与核对） | 1 分钟/店（含节流等待） |
| 单批 30 家 | 约 2-3 小时 | 约 30 分钟无人值守（1 分钟/店） |
| 发送对象准确率 | 依赖人工核对 | 三重校验；可疑门店自动拦截转人工核对 |
| 中断恢复 | 需人工重新核对断点 | 幂等重跑，自动跳过已完成 |
| 留痕 | 手工记录、易缺失 | 每店截图 + 时间戳自动归档，全量可追溯 |
| 本地数据残留 | 截图散落个人电脑 | 成功后本地自动清理，证据仅存飞书 |

**典型运行参数**：系统吞吐 1 分钟/店 · 单批 30 家（约 30 分钟） · 批次间不跨优先级 · 每店 8-15 秒随机节流 · 单批可随时 Ctrl+Z 暂停 · 失败自动隔离并保留证据。

## 五、方案可迁移场景

同一套「数据源 → 卡片/消息 → IM 定向触达 → 截图回传归档」的骨架，可直接迁移到：

- **连锁零售/餐饮**：门店日报、达标提醒、促销任务下发与回执
- **企微私域运营**：客户分层触达、活动通知、SOP 检查
- **总部 → 分部/经销商**：政策下发、数据周报、任务跟进闭环
- **IT/运维通知**：系统告警定向推送 + 处理留痕
- **任何"飞书表格 + 企业微信"组合的重复人工流程**

扩展方式：更换数据源表结构、话术模板与目标筛选规则即可，无需重写核心引擎。
